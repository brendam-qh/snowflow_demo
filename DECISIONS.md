# SNOWFLOW — Deviations & Decisions

## Stack
- **Keep Babylon.js 9.18 + hand-written WGSL** (PRD §2 said Three.js/TSL). The repo is entirely Babylon; rewriting would discard ~40 working shaders and all orchestration with no visual upside. Physics + SSFR intent is ported to Babylon's ComputeShader/StorageBuffer/PostProcess instead.
- **`shader-f16` requested but not required.** If the adapter (Safari/Webkit) lacks it, fall back to f32 with a console warning rather than no water. PRD §5 wanted f16 mandatory; not worth a hard failure on the primary target browser.

## Bugs found + fixed in upstream shaders
- `heightBake.fragment.wgsl` used `vary vUV: vec2f;` (typo for `varying`). Babylon's WGSL preprocessor handles `varying` only; bare `vary` reached the WGSL compiler unreplaced and the RG32F heightfield bake never ran, so the CPU mirror stayed null (character floated at y=0) and the rendered terrain effectively lost its macro displacement. Fixed to `varying`. This bug exists in the original commit too — it only didn't manifest because the deploy schema picked a less strict WGSL parser.
- Renamed `enable`, `cross` (WGSL reserved/builtin name collisions) in the new `riverChannel` function signature.

## Validation constraint
- This assistant has no image-vision: visual milestone gates are supplied via per-pixel/luma statistics (`scripts/pstat.mjs`) and the user is asked to look at `shots/*.png` directly. Numbers can flag hard failures (flat frame, no carving) but cannot judge composition, light, or polish.

## Terrain
- **River shape baked once at boot.** Like the dune heightfield, `riverness`/`riverWidth`/`riverDepth`/`riverFlowDir` feed the bake; changing them at runtime needs a re-bake (deferred). Re-baking every drag would tank the load screen.

## Render
- **MVP river surface before full SSFR.** SPH is in scope but the first visible milestone is a shader-driven kinematic surface flowing down the valley gradient, gated behind `S.fluidMode`. Build order: valley → MVP surface → SPH → SSFR. The PRD §6 phase order is preserved; only my visible-milestone order changes.
- **M2 spawn bank scan, not fixed offset.** `main.js` originally placed the character at a hardcoded `_perp * BANK_OFFSET = 50m`; the bed meanders, and at the spawn's `along=0` the channel centre had wandered ~85m off, leaving only a thin upper wedge of river in frame. Replaced with a post-`terrain.build()` scan that finds the deepest point on the perpendicular, walks outward each side until ground rises above `waterY=−15` (the shoreline), and drops the spawn 3m past the higher shoreline looking across at the bed centre. `charY≈−13.3` vs `waterY=−15` ⇒ character stands on the bank.
- **M2 river surface shader retune.** Original `river.fragment.wgsl` rendered almost invisibly (controlled A/B: ~3 coarse cells of 48 differ, uniform +9 luma gray). Three causes: (1) sky-Fresnel cap at 0.78 saturated at the glancing spawn view and turned the surface into a sky-mirror; (2) deep tint was navy `(0.045, 0.115, 0.165)` not teal; (3) the refracted-snow pull at 0.45 washed teal against the already-teal wet riverbed beneath. Fixed: `WATER_ABSORB` deepened to `(4.6, 1.0, 0.42)` with path scale `bedMask*5.0`, deep tint repointed to true teal `(0.018, 0.115, 0.075)` (green-dominant), Fresnel cap lowered to 0.08, refracted-snow mix cut to 0.12, sun-glint strengthened (`rough=0.030`, ×1.2), alpha floor risen. Water region now samples `(24,52,67)` at depth.
- **`S.riverWidth` default 1.0 → 0.35.** Original channel was a wide basin; narrowed to ~⅓ so the banks frame the river as a channel. Slider min lowered 0.4 → 0.15 so the new default isn't pinned at the floor.

## Fluid (M3)
- **PIC/FLIP hybrid, not pure SPH.** PRD §3 lists "SPH **or** PIC/FLIP" — either is in spec. For a *river* (steady channel flow with open inflow/outflow boundaries and wading-character interaction), PIC/FLIP is the physically better fit: more stable, less compressible, cleaner boundary handling. SPH's scatter-neighbour-search machinery is overkill at this scale. Visual outcome (advected marker particles rendered via the M4 SSFR pass) is identical between the two for a river.
- **Grid solve on `ProceduralTexture`, particles on `StorageBuffer`+`@compute`.** The grid velocity/pressure field maps 1:1 onto the existing `deformSim` fragment-on-`ProceduralTexture` pattern (two RGBA textures, ping-pong, `pt.render()`) — zero new infrastructure, matches every warm-up convention, and Apple TBDR perf is better without tile flushes (PRD §5 warning honored). The marker *particles*, however, are the half that genuinely wants `var<storage>` + `@compute`: fragment passes have no `atomicAdd`, so particle→grid density scatter and parallel neighbour sort are not cleanly expressible there. This hybrid is exactly the PRD §3 contract ("StorageBuffer + `atomicAdd` for scatter, parallel prefix-sum sort, tens of thousands of particles, no CPU readback") applied to the half of the solver that needs it, while the grid half stays on the proven texture path. Introduces the repo's first `StorageBuffer`/`@compute` — a 0→1 break, but only for the particle subsystem; the warm-up pattern mirrors `deformSim.warmUp()` with a `whenReady` on the compute pipeline.
- **M3 particle renderer is billboard quads, not true SSFR (yet).** PRD §4 calls for screen-space fluid reconstruction — depth pass → bilateral blur → thickness → normal reconstruction. The current `ParticleRenderer` (`src/fluid/particleRender.js`) is a simpler first step: 16K camera-facing quads (one per particle) of `particleSize` width, vertex shader reads positions from the particle `StorageBuffer` via `var<storage, read>` bound through `ShaderMaterial.storageBuffers`. Sufficient to verify particles are alive and in the river bed, but it has two known gaps TODO:
    - **Depth test:** billboards currently render through terrain (39% of the frame changes when toggled, including sky), so the depth-stencil configuration is wrong rather than the particles being outside the bed. The `disableDepthWrite = true` shared with the river material is the same flag, so this is likely a column-relative thing rather than a missing flag.
    - **SSFR pass:** the proper pipeline (depth pre-pass → bilateral blur → thickness → normals from smoothed depth) is the M4.5 deliverable. The renderer is gated behind `S.fluidMode === "full"` so it doesn't affect the default "off" / "particles" demos.

## Webcam tracking (2026-08-18)
- **Tracking integrated in-repo, not bridged from the sibling React app.** The root repo's head-tracker is React/Three.js; snowflow is vanilla JS/Babylon. A postMessage bridge would add latency and a second app to run for zero reuse that matters — the MediaPipe glue is ~100 lines.
- **`@mediapipe/tasks-vision@1.0.0-rc.20260727` pinned exactly.** The `.npmrc` supply-chain gate is `before=2026-07-28`; this RC (published 2026-07-27) is the newest that passes. Newer RCs sit inside the 7-day quarantine.
- **npm kept, not bun.** The repo-wide convention is bun, but this project's README/scripts are npm + `package-lock.json` (and the `.npmrc` gate is npm-flavoured). Project convention wins; recorded here per the global rules.
- **First third-party assets in the repo.** `public/models/*.task` + wasm are runtime ML models, not render assets — the rendered world is still 100% procedural. Vendored locally so there is no CDN dependency.
- **Head-look is an absolute composition-time offset, not a projection change.** True off-axis projection fights TAA jitter, the post chain and the shadow passes; adding yaw/pitch offsets where the rig composes its transform keeps every pass untouched, and self-centers (turn back, view returns) with no drift. `getFlatForward/Right` compose the same offset the view does, so walking follows the look: glance left and W walks left. (Reversed 2026-08-31. The original decision excluded the offset so head movement could never steer the character; coupling them reads better in the demo, and because the offset is absolute and self-centering, facing the screen again puts W back where it was.)
- **Gestures write into the shared `input` struct after `pollInput()`.** One seam, one arbitration point: the gesture layer owns movement only while a hand is confidently tracked, zeroes it once on loss (~250 ms), and releases a held Ribbon — stale input can never run the character off.
- **Spell gestures are edge-triggered with a 2-frame confirm and a return-to-neutral re-arm**, so a held pose is never a burst of casts. `spellStats` exists because `spellPressed` lives for exactly one frame and is therefore unobservable to e2e polling.
- **Playwright runs headed by default.** Headless Chromium's WebGPU adapter (SwiftShader) can create a device but not present to a canvas — boot crashes there. `E2E_HEADLESS=1` forces headless for CI, in which case the smoke test skips itself if boot fails.
